# PART A — DESIGN-LEVEL SPECIFICATION
# 1. Purpose and Scope
The GenAI layer translates machine signals into human-usable intelligence: narratives, ranked hypotheses, audience-specific communications, runbooks, post-incident reports and structured labels from analyst notes. It does not make detection or severity decisions. It is consumed by TS-08 (ticket enrichment) and by agents (TS-14/15) as GenAI tools.
# 2. Component Decomposition
| Sub-component | Responsibility |
|---|---|
| LLM gateway | Single internal API for all LLM calls; provider abstraction, routing, quotas, redaction, logging, caching, fallback |
| Prompt registry | Versioned prompt templates and output schemas per function |
| RAG service | Query construction, hybrid retrieval, re-ranking, context assembly |
| Indexer | Chunking and embedding of six knowledge sources; incremental updates |
| Vector store | Dense index (pgvector, Weaviate or Pinecone) + sparse BM25 index (OpenSearch) |
| Grounding validator | Checks factual claims in outputs against structured incident payload |
| Enrichment worker | Asynchronous orchestration of GenAI functions for incidents |
# 3. Key Design Decisions
| Decision | Rationale |
|---|---|
| Model-agnostic gateway | Swap providers or self-hosted models without downstream change; supports data-residency profiles |
| One task per LLM call | Predictable outputs and simpler evaluation |
| Structured JSON outputs validated against schema | Machine-consumable by agents and ITSM |
| Asynchronous enrichment; never blocks incident creation | Incident SLA independent of LLM availability |
| Hybrid retrieval (dense + BM25) with reciprocal rank fusion and cross-encoder re-rank | Captures both semantic similarity and exact identifiers (service names, error codes) |
| Deterministic grounding validation outside the model | Hallucinated metric values or entities are rejected before reaching any external system |
# 4. Non-Functional Requirements
| ID | Requirement |
|---|---|
| TS13-NFR-001 | Narrative + hypothesis enrichment ≤ 10 s P95 from incident creation |
| TS13-NFR-002 | Average tokens per incident ≤ 4,000 input / 800 output per function call |
| TS13-NFR-003 | LLM factual accuracy ≥ 98% of quantitative claims grounded (TS-17 KPI) |
| TS13-NFR-004 | No incident data transits public endpoints unless residency profile permits; private connectivity otherwise |
| TS13-NFR-005 | New resolved incidents indexed for retrieval ≤ 5 min after resolution |
# PART B — LOW-LEVEL SPECIFICATION
# 5. LLM Gateway
## 5.1 API
```
POST /v1/generate
{
  "function": "incident_narrative",          // registered function id
  "prompt_version": "incident_narrative@3",
  "incident_id": "0192f0c1-...",
  "inputs": { ... },                          // function-specific structured inputs
  "max_output_tokens": 800,
  "deadline_ms": 8000,
  "caller": "triage-agent@1.4.0"
}
-> 200 { "output": {...schema-valid JSON...}, "model": "<provider>/<model>@<ver>", "usage": {"in": 3120, "out": 412},
         "grounding": {"status": "pass", "claims_checked": 9, "violations": []}, "latency_ms": 4310 }
-> 422 { "error": "schema_violation" | "grounding_failed", "attempts": 2 }
-> 503 { "error": "provider_unavailable", "fallback": "queued" }
```
## 5.2 Gateway processing
1. AuthN caller (mTLS identity) and check function entitlement and per-caller quota.
2. Load prompt template and output schema from registry by `prompt_version`.
3. Assemble context (RAG call where function requires) and apply **prompt compression**: drop low-relevance chunks, summarise timelines beyond 10 events, cap at 4,000 tokens.
4. **Redaction** (PRIV-04): regex + NER pass for emails, phone numbers, card-like numbers (Luhn-checked), national-ID patterns, secrets (high-entropy tokens, key prefixes), IPs optionally hashed per profile.
5. Route to provider per policy (primary, secondary); temperature 0.1–0.3 per function; JSON/structured-output mode where provider supports.
6. Validate output against JSON schema; on failure re-prompt once with validator errors.
7. Run grounding validator (§9); on failure re-prompt once with violations listed; second failure → return 422 and emit structured-only fallback.
8. Log request metadata, prompt hash, output, usage and grounding result to audit (prompt text retained per retention profile).
## 5.3 Provider routing policy
```
providers:
  primary:   { type: managed_api, model: "<frontier-model>", region: "<in-region>", private_link: true }
  secondary: { type: managed_api, model: "<alternative-frontier-model>", region: "<in-region>" }
  local:     { type: self_hosted, model: "<open-weights-model>", endpoint: "http://vllm.genai:8000" }
routing:
  default: [primary, secondary]
  profile.llm.self_hosted_only: [local]
  function.analyst_note_parsing: [local, primary]     # high volume, lower complexity
timeouts: { connect_ms: 1000, first_token_ms: 4000, total_ms: function.deadline_ms }
circuit_breaker: { failures: 5, window_s: 60, open_s: 30 }
cache: { key: hash(prompt_version, inputs_canonical), ttl: PT10M, functions: [incident_narrative] }
```
# 6. RAG Pipeline
## 6.1 Knowledge sources and indexing
| # | Source | Chunking | Metadata stored | Update trigger |
|---|---|---|---|---|
| 1 | Incident history | One chunk per incident summary + one per root-cause/resolution section (≤ 512 tokens) | services, entities, failure_mode, severity, dates, duration, outcome | On resolution (≤ 5 min) |
| 2 | Runbook library | By procedure step group (≤ 400 tokens, 50 overlap) | runbook_id, services, failure_modes, last_reviewed | On Git commit |
| 3 | Change records | One chunk per change | CIs, type, start/end, risk, outcome | Webhook, real time |
| 4 | Service dependency graph | Per-service neighbourhood text summary (2-hop) | service, tier, owners | CMDB delta |
| 5 | Known error database | One per known error | symptoms, workaround, permanent_fix_status | On update |
| 6 | Team & escalation directory | Per team/service | on-call schedule ref, escalation chain | Hourly sync |
Embedding model: configurable (e.g. a 1,024–3,072-dim general embedding model or self-hosted equivalent); all chunks store `embedding_model_version`; re-embedding job runs on model change.
## 6.2 Retrieval algorithm
```
query = build_query(function, incident)        # signals, service names, error templates, predicted mode
dense  = vector_search(embed(query), k=40, filter=source_filter(function), recency_boost)
sparse = bm25_search(query_terms ∪ identifiers, k=40, filter=source_filter(function))
fused  = reciprocal_rank_fusion([dense, sparse], k_rrf=60)        # score = Σ 1/(60 + rank)
top    = cross_encoder_rerank(query, fused[:30])[:N_function]       # N: narrative 3, hypotheses 5, runbook 5, PIR 5
context = [ {source_type, id, relevance, age_days, text} for c in top ]
```
Source filters per function: narrative {1,4}; hypotheses {1,3,4,5}; comms {4,6}; runbook {2,1,5}; PIR {1,3}; note parsing {none}.
Recency boost for change records: score × exp(−age_hours / 4). Incident-history retrieval excludes the current incident and any incident still open.
# 7. Prompt Framework
## 7.1 Template structure
```
[SYSTEM]
You are a senior SRE/NOC analyst. Be factual and concise. Use only facts present in <incident_context> or <retrieved>.
Never invent metric values, timestamps, hostnames, IPs or service names. If information is missing, set the field to null and list it in "missing_information".
Cite the source_type for any statement drawn from <retrieved>. Output must match the JSON schema exactly.
[USER]
<task>{function-specific instruction}</task>
<incident_context>
  <severity>P2</severity><rationale>…</rationale>
  <affected_entities>…</affected_entities>
  <timeline>(last 10 events)</timeline>
  <signal_clusters>(top 3)</signal_clusters>
  <cmdb>…</cmdb><service_health>…</service_health>
</incident_context>
<retrieved>
  <doc source_type="incident_history" id="INC0078811" relevance="0.82" age_days="41">…</doc>
</retrieved>
<output_schema>{JSON Schema}</output_schema>
```
## 7.2 Function catalogue
| ID | Function | Trigger | Inputs | Output schema (key fields) | Quality gate |
|---|---|---|---|---|---|
| F1 | Incident narrative | Incident `create` | Payload, top 3 retrieved | `summary` (3–5 sentences), `affected_services[]`, `symptoms[]`, `missing_information[]` | Schema + grounding; length 40–120 words |
| F2 | Root-cause hypothesis ranking | After correlation / Diagnostic agent evidence | Payload, evidence bundle, top 5 similar incidents | `reasoning_chain` (separate field), `hypotheses[{rank, cause, entity, evidence[], confidence_rationale, similar_incidents[]}]` | Every hypothesis references ≥ 1 evidence item present in input |
| F3 | Stakeholder communications | P1/P2 create; periodic updates | Payload, narrative, status | `bridge_update`, `executive_summary`, `status_page_update` (each with audience-specific constraints) | Status page: no internal hostnames/IPs; executive ≤ 120 words; banned-phrase list |
| F4 | Dynamic runbook generation | No runbook match or match stale > 90 d | Payload, service context, known errors | `steps[{n, action, command_or_check, expected_result, tier_suggestion, rollback}]`, `assumptions[]` | Marked `generated=true`; commands validated against allow-listed tool syntax; Tier suggested ≥ registry tier |
| F5 | Resolution summary & PIR | Incident resolved | Full ISO, timeline, actions, notes | `timeline[]`, `root_cause`, `contributing_factors[]`, `resolution_steps[]`, `customer_impact{start,end,minutes}`, `preventive_actions[]` | Timestamps must match ISO; durations recomputed and checked |
| F6 | Analyst note parsing | Note added to ticket | Note text, incident summary | `is_false_positive{value,confidence}`, `root_cause_class`, `severity_assessment_delta`, `remediation_steps[]` | Confidence < 0.7 → label not auto-applied; queued for review |

# 9. Grounding Validator
| Claim type | Extraction | Check against |
|---|---|---|
| Numeric metric values | Regex for numbers with units / % near metric names | Payload timeline and signal values (tolerance ±1% or ±1 unit) |
| Timestamps / durations | Datetime parser | Payload and ISO timestamps (±60 s); durations recomputed |
| Entity / service names | Dictionary match | Payload entities, CMDB names in context |
| IPs, hostnames | Regex | Payload only |
| Incident references | Pattern (`INC\d+` etc.) | Retrieved document ids |
| Evidence refs (F2) | Schema field | Evidence bundle ids |
Result: `pass` if all extracted claims verify; `fail` lists violations. Validation outcome is stored and feeds the LLM factual-accuracy KPI.
# 10. Cost, Latency and Fallback
| Item | Specification |
|---|---|
| Token budget | Per call: ≤ 4,000 in / 800 out average; hard cap 8,000 / 1,500 |
| Monthly budget guard | Spend tracked per function; at 80% of budget, F3 periodic updates move to 30-min cadence and F6 routes to local model; at 100%, only F1/F2 for P1/P2 |
| Latency | Gateway P95 ≤ 8 s per call; F1+F2 run in parallel |
| Fallback | Provider down or deadline exceeded → incident keeps structured payload; job queued with retry (1, 5, 15 min); applied retrospectively with note "enrichment delayed" |
| Never-block rule | No ITSM create or agent tier-1 action waits on GenAI |
# 11. Evaluation
| Metric | Method | Target |
|---|---|---|
| Factual accuracy | Grounding validator pass rate + monthly human audit of 100 outputs | ≥ 98% |
| Hypothesis top-3 hit rate | Confirmed root cause ∈ top 3 | ≥ 75% (Month 12) |
| Narrative usefulness | Analyst rating 1–5 on sample | ≥ 4.0 |
| Retrieval quality | Recall@5 on labelled query set (200 queries) | ≥ 0.8 |
| Regression | Golden-set replay (50 incidents per function) on every prompt or model change | No metric drop > 2 points |
# 12. Security Controls
| ID | Control |
|---|---|
| TS13-SEC-001 | Prompt-injection defence: retrieved and ticket-derived text wrapped in data tags; instructions inside data ignored by system prompt; pattern scanner flags injection phrases and strips them; outputs never executed directly |
| TS13-SEC-002 | Provider contracts: no training on submitted data; zero/limited retention; in-region processing per profile |
| TS13-SEC-003 | Vector store access scoped per org unit (metadata filter enforced server-side) |
| TS13-SEC-004 | Prompt and output logs subject to the same retention and access as incident records |
# 13. Acceptance Criteria
| ID | Criterion |
|---|---|
| TS13-AC-001 | F1+F2 complete ≤ 10 s P95 on 500 replayed incidents |
| TS13-AC-002 | Provider outage: incidents still created on time; enrichment applied after recovery |
| TS13-AC-003 | Injected hallucination test (seeded wrong values in model output via test double) is caught by grounding validator 100% |
| TS13-AC-004 | Status-page outputs contain zero internal hostnames/IPs on test set |
| TS13-AC-005 | Prompt-injection test corpus (100 cases in notes/logs) produces no instruction-following in outputs |
