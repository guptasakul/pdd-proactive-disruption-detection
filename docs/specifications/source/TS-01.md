# PART A — DESIGN-LEVEL SPECIFICATION
# 1. Purpose and Scope
This specification fixes the system boundary and the requirements baseline for the solution, and defines the five-layer reference architecture and the contracts between layers. Component specifications TS-02 to TS-16 MUST trace their requirements to the system requirements in Section 5.
**In scope:** detection of impending infrastructure, application, data and security disruption from telemetry; automated creation and enrichment of incidents; GenAI enrichment and agent-driven response within a governed safety envelope; self-management of the solution itself.
**Out of scope:** replacing the organisation's ITSM platform, SIEM, APM or observability stores; business continuity decisions; customer-facing communication content approval (the solution drafts, humans approve unless configured otherwise); remediation of Tier 4 actions (TS-16).
# 2. Problem Definition
The solution addresses six operational failure patterns. Each is restated as a design driver with the mechanism that answers it.
| ID | Problem | Design driver | Primary mechanism (spec) |
|---|---|---|---|
| P-1 | Dynamic environments make static thresholds unreliable | Thresholds MUST be learned per entity and per context | Four-layer baselining (TS-06) |
| P-2 | Cascade failures propagate across microservice dependencies | Detection MUST reason over topology, not only per-entity metrics | GNN model (TS-05), dependency graph (TS-03 CMDB resolution) |
| P-3 | Threats mimic benign traffic | Security signals MUST be scored behaviourally, not only by signature | Behavioural features (TS-04), security domain sources (TS-02) |
| P-4 | Alert fatigue from false positives | False positive rate on auto-created tickets MUST stay below 5% | Five-filter suppression (TS-07), feedback loop (TS-11) |
| P-5 | Fragmented visibility across tools | All telemetry MUST be normalised to one schema with resolved entities | ECS normalisation, entity resolution (TS-03) |
| P-6 | Reactive posture | Incidents MUST be raised from precursor signals before user impact | Transformer precursor model (TS-05), proactive detection KPI (TS-17) |
> Working premise carried from the white paper: 60–80% of production outages show detectable precursor signals 15–60 minutes before user impact. The solution's value depends on this premise holding in the target estate; TS-17 Phase 1 validates it against 90 days of historical incidents before Phase 3 automation is enabled.

# 4. Reference Architecture
## 4.1 Five processing layers
| Layer | Name | Function | Specifications |
|---|---|---|---|
| L1 | Data Collection | Collect logs, metrics, traces and events via OpenTelemetry from six observability domains | TS-02 |
| L2 | Ingestion & Normalisation | Aggregate, deduplicate, normalise to ECS, resolve entities, enrich, extract features | TS-03, TS-04 |
| L3 | ML Pattern Analysis | Score feature streams with a five-model ensemble against four-layer baselines | TS-05, TS-06 |
| L4 | Decision & Classification | Suppress false positives, assign P1–P4, construct incident payload | TS-07 |
| L5 | Incident Orchestration | Create and manage incidents in ITSM; notify; collect feedback | TS-08 |
## 4.2 Cross-cutting planes
| Plane | Function | Specifications |
|---|---|---|
| Intelligence plane | GenAI enrichment; six-agent network acting on incidents | TS-13, TS-14, TS-15 |
| Control plane | Governance, self-management, self-correction, agent safety | TS-10, TS-11, TS-16 |
| Infrastructure plane | Kubernetes runtime, HA/DR, scaling, security controls | TS-09, TS-12 |
## 4.3 End-to-end data flow
```
[Sources: 6 domains] --OTLP/syslog/API--> [OTel Collectors] --Kafka raw.<domain>--> 
[Flink: aggregate, dedup, normalise, resolve, enrich] --Kafka norm.events--> 
[Flink: feature extraction 1m/5m/1h] --> [Feature Store (Redis)] + Kafka features.vectors
      --> [ML Inference: LSTM-AE | IsoForest | GNN | Transformer | SPC] --> [Score Fusion]
      --Kafka ml.detections--> [Decision Engine: suppress, classify, payload]
      --Kafka decision.incidents--> [ITSM Integration] --> ServiceNow / PagerDuty / JSM / OpsGenie / Slack
                                  \--> [Orchestrator Agent] --> Triage / Diagnostic / Comms / Remediation / Learning
ITSM feedback --Kafka feedback.labels--> [Learning Agent / retraining queue] --> [Model Registry] --> ML Inference
```
## 4.4 Architectural principles
| Principle | Obligation on component specifications |
|---|---|
| Open standards | Collection MUST use OpenTelemetry (OTLP); schemas MUST be registered (Avro/Protobuf); no proprietary agent is mandatory |
| Event-driven | Inter-layer communication MUST be asynchronous via Kafka topics; synchronous calls are limited to look-ups with timeouts and fallbacks |
| Defence in depth | No single model, filter or agent is a single point of detection; each layer degrades gracefully |
| Explainability | Every score, decision and agent action MUST carry machine- and human-readable rationale |
| Independently replaceable layers | Each layer MUST be replaceable behind its contract (topic schema or API) without changing adjacent layers |
| Human authority | Humans MUST be able to pause, override and reverse automated behaviour at every layer (TS-16 kill switch) |

# PART B — LOW-LEVEL SPECIFICATION
# 6. Inter-Layer Contracts
All inter-layer contracts are Kafka topics with schemas registered in the Schema Registry under `BACKWARD_TRANSITIVE` compatibility. Topic names follow `<layer>.<object>[.<qualifier>]`.
| Topic | Producer | Consumers | Key | Schema subject | Partitions (baseline) | Retention |
|---|---|---|---|---|---|---|
| `raw.network` / `raw.security` / `raw.application` / `raw.database` / `raw.platform` / `raw.business` | OTel Collector gateway | Normaliser (TS-03), archiver | `source_host` | `raw.<domain>-value` (Avro envelope) | 96 each | 72 h (12 h local, rest tiered) |
| `norm.events` | Normaliser | Feature extractor, log store sink | `entity_id` | `norm.events-value` (ECS Avro) | 192 | 72 h |
| `norm.deadletter` | Normaliser | Data engineering triage | `source_id` | `norm.deadletter-value` | 12 | 14 d |
| `features.vectors` | Feature extractor | ML inference, training materialiser | `entity_id` | `features.vectors-value` | 192 | 24 h |
| `ml.detections` | Score fusion | Decision engine, audit | `entity_id` | `ml.detections-value` | 48 | 7 d |
| `decision.incidents` | Decision engine | ITSM integration, Orchestrator agent | `incident_id` | `decision.incidents-value` | 24 | 30 d |
| `feedback.labels` | ITSM integration, Learning agent | Retraining queue, suppression manager | `incident_id` | `feedback.labels-value` | 12 | 90 d |
| `control.config` | GitOps controller | All components (hot-reload) | `component` | `control.config-value` | 1 | compacted |
| `audit.trail` | All components | Audit sink (immutable store) | `object_id` | `audit.trail-value` | 24 | 7 d (sink is system of record) |
## 6.1 Common envelope (all topics)
```
record Envelope {
  string  schema_version;        // semver of payload schema
  string  message_id;            // UUIDv7
  long    produced_at_ms;        // UTC epoch ms
  string  producer;              // component@version
  string  trace_id;              // W3C traceparent trace-id for pipeline tracing
  map<string> tenancy;           // org_unit, environment (prod|nonprod), region
  bytes   payload;               // typed per subject
}
```
## 6.2 Delivery semantics
| Hop | Semantics | Mechanism |
|---|---|---|
| Collector → `raw.*` | At-least-once | Producer `acks=all`, idempotence on, collector disk buffer |
| `raw.*` → `norm.events` → `features.vectors` | Exactly-once | Flink checkpointing + Kafka transactional sink |
| `features.vectors` → `ml.detections` | At-least-once, idempotent consumer | Detection keyed by `feature_vector_id`; duplicates dropped in decision engine |
| `decision.incidents` → ITSM | Effectively-once | Idempotency key = `incident_id`; ITSM correlation_id lookup before create |
# 7. Environment and Tenancy Model
- Environments: `prod`, `preprod`, `dev`. Production telemetry MUST NOT flow to non-production environments; non-production models train on synthetic or masked replays only.
- Multi-tenancy: an organisational unit label (`tenancy.org_unit`) is carried on every event and incident. RBAC policies and ITSM routing are scoped by org unit.
- Regions: each region runs a full stack (TS-09); cross-region correlation operates on `ml.detections` and `decision.incidents` only, never raw telemetry, so that data residency rules can be enforced per region.
# 8. Context-Level Failure Modes
| Failure | Detection | System behaviour | Spec |
|---|---|---|---|
| Kafka cluster unavailable | Producer error rate, controller health | Collectors buffer to disk (≥ 2 h at baseline rate); detection paused; platform P1 raised via out-of-band path | TS-03, TS-09 |
| ML inference unavailable | Readiness probe, queue depth | SPC fast-path continues in Flink (degraded mode); incidents carry `degraded_detection=true` | TS-05 |
| Decision engine unavailable | Consumer lag on `ml.detections` | Detections queue; no incidents created; out-of-band alert to platform team | TS-07 |
| ITSM unavailable | 3 consecutive API failures | Circuit breaker opens; incidents queued for replay; fallback page via secondary channel | TS-08 |
| LLM unavailable | Gateway timeout / 5xx | Incidents created with structured payload only; enrichment replayed later | TS-13 |
| Agent misbehaviour | Rate-limit breach, guardrail violation | Agent paused by circuit breaker; Orchestrator routes to human | TS-16 |
| Solution itself silent | Heartbeat absence | External dead-man's-switch (independent synthetic) pages platform on-call if no heartbeat for 5 min | TS-11 |
> The solution MUST NOT be the only path by which its own failures are reported. A dead-man's-switch hosted outside the solution's failure domain is mandatory.
