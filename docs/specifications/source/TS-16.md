# PART A — DESIGN-LEVEL SPECIFICATION
# 1. Purpose and Scope
Autonomous agents acting on production carry inherent risk. This specification bounds that risk with three principles: constrain actions to a pre-approved envelope; make every action transparent and, where possible, reversible; and let humans take control instantly. All controls here are enforced in the tool execution layer (TEL, TS-14 §7) and cannot be altered by agent reasoning.
# 2. Safety Principles to Controls
| Principle | Controls |
|---|---|
| Constrain | Fixed tier classification; capability profiles; scope boundaries; rate limits; blast-radius cap; production lock |
| Transparent and reversible | Mandatory audit with reasoning trace; irreversibility gate; one-click reversal; post-action verification |
| Human control | Kill switch; per-agent pause; approval workflows; confidence floor; human-only Tier 4 |
# 3. Non-Functional Requirements
| ID | Requirement |
|---|---|
| TS16-NFR-001 | Kill switch effective (no new actions) ≤ 5 s in scope |
| TS16-NFR-002 | Guardrail evaluation adds ≤ 50 ms P99 to tool calls |
| TS16-NFR-003 | 100% of agent actions auditable with reasoning; audit retained ≥ 24 months |
# PART B — LOW-LEVEL SPECIFICATION
# 4. Action Safety Tiers
| Tier | Class | Examples | Execution rule |
|---|---|---|---|
| 1 | Safe — autonomous | Log/metric/trace reads, ITSM ticket create/comment, chat notifications, runbook retrieval, status page draft | Execute; audit |
| 2 | Low risk — notify | Stateless pod restart, cache flush, connection pool reset, read-only cloud API calls, scaling within pre-set bounds | Execute; audit; notify on-call simultaneously |
| 3 | Approval required | Scaling beyond bounds, feature-flag changes (non-ops-reversible), config updates, deployment rollback, DB query execution | Explicit approval by on-call engineer (chat button or ITSM workflow); 10-min timeout → escalate |
| 4 | Human only | Production DB modifications, DNS changes, firewall rules, security groups, cross-region failover | Agent prepares proposed action + guidance; never executes |
## 4.1 Classification governance
- Tier is a property of the tool definition in the registry; agents cannot set or request reclassification at runtime.
- New tools default to Tier 4 until classified by AI Governance + service owner; reclassification to a lower tier requires CAB approval and 30 days of shadow evidence (tool proposed by agents, executed by humans, outcomes compared).
- Effective tier = max(registry tier, phase cap, profile cap `agents.max_tier`, guardrail escalations).
## 4.2 Phase caps
| Implementation phase (TS-17) | Max autonomous tier |
|---|---|
| Phase 1 | None (GenAI enrichment only) |
| Phase 2 | Tier 1 (Triage, Comms) |
| Phase 3 | Tier 2 autonomous; Tier 3 with approval |
| Phase 4 | Tier 2 autonomous; Tier 3 with approval (unchanged); Tier 4 never |
# 5. Hard Guardrails
| Guardrail | Rule | Default | On trip |
|---|---|---|---|
| G1 Rate limiting | Per-agent per-minute and per-hour; per-incident action cap | Triage ≤ 10 tickets/min; Remediation ≤ 5 actions/incident, ≤ 20/h global | Circuit breaker pauses agent; human alerted |
| G2 Scope boundary | Agent acts only within declared service scope | Scope = services in incident at dispatch | Cross-scope → Orchestrator approval; logged as cross-boundary event |
| G3 Irreversibility gate | Tier ≥ 2 requires registered rollback | — | Reclassify to Tier 4 |
| G4 Blast-radius cap | Computed radius ≤ affected service + direct dependencies | Depth 1 | Escalate to Tier 3 |
| G5 Hallucination mitigation | LLM factual claims validated vs. payload before writing to any external system | TS-13 §9 | Reject output; re-prompt once; then fallback |
| G6 Production lock | During change freeze, major-incident window, declared maintenance | From change calendar + CMDB | Tier ≥ 2 blocked |
| G7 Duplicate action | Same tool + params twice in an incident | — | Block; escalate |
| G8 Parameter bounds | Numeric params within tool-declared min/max (e.g. replicas) | Per tool | Reject |
| G9 Time-of-day policy (optional) | Restrict Tier 2 for selected services in business-critical windows | Off | Escalate to Tier 3 |
## 5.1 Guardrail evaluation order
`identity → capability → kill/pause → G6 → G2 → G1 → G8 → G7 → G3 → G4 → tier policy → lock → execute`. The first failing check determines the outcome; all checks evaluated are recorded in the audit record.
## 5.2 Policy as code (example)
```
package tel.guardrails
default allow = false
allow {
  input.tool.tier <= effective_cap
  not paused[input.agent][input.scope]
  not production_locked(input.target.service)
  in_scope(input.agent, input.target.service)
  within_rate_limits(input.agent, input.tool, input.incident_id)
  has_rollback(input.tool) ; input.tool.tier >= 2
  blast_radius(input) <= max_radius(input.target.service)
}
effective_cap := min([data.phase_cap, data.profile.max_tier, input.tool.tier_override_cap])
```
Policies are evaluated by an embedded OPA engine in TEL; policy bundles are signed and delivered via GitOps.
# 6. Approval Workflow (Tier 3)
| Step | Detail |
|---|---|
| Request | Card to on-call (chat) and ITSM approval task: action, params, rationale, evidence summary, expected outcome, risk, blast radius, rollback plan, expiry |
| Approver eligibility | On-call engineer for the target service or incident manager; approver ≠ change author; MFA-backed session |
| Decision | Approve / Reject / Approve with conditions (e.g. "only replicas ≤ 12"); conditions are applied as parameter constraints |
| Timeout | 10 min → escalate to secondary on-call; request expires at 20 min |
| Execution | TEL re-validates guardrails at execution time (state may have changed) |
| Record | Approver identity, channel, timestamp, conditions in audit and ISO |
# 7. Agent Audit Record
| Field | Content |
|---|---|
| `timestamp` | UTC, ms precision |
| `agent` | Name, version, instance id, workload identity |
| `incident` | Incident id, severity and lifecycle stage at time of action |
| `reasoning_trace` | Verbatim Think output that selected the action (or pointer to stored trace) |
| `action` | Tool name, version, parameters, effective tier, guardrail checks evaluated and results |
| `response` | Raw API response (truncated at 64 KiB with hash of full body) |
| `outcome` | success / failure / partial / denied / pending_approval, with error detail |
| `iso_snapshot` | ISO version hash before and after |
| `approval` | Approver identity, channel, timestamp, conditions (if applicable) |
| `reversal` | Rollback availability, reversal action id if reversed |
Storage: append-only (TS-10 §6), retained ≥ 24 months, excluded from standard purge, not deletable by agents or services.
# 8. Human Override and Control
| Control | Interface | Behaviour | Target latency |
|---|---|---|---|
| Kill switch | CLI/API `POST /v1/control/kill {scope: incident|service|all, reason}`; UI button; chat command for incident managers | Sets kill flag in control store (replicated Redis + `control.config` event); TEL denies new actions; in-flight calls complete; agents enter paused state | ≤ 5 s |
| Agent pause | `POST /v1/control/pause {agent, scope}` | Orchestrator routes that agent's tasks to humans with context | ≤ 5 s |
| Action reversal | ITSM ticket action / chat button on any Tier 2 action ≤ 60 min old | Remediation agent executes registered rollback; audited as reversal | ≤ 60 s to start |
| Confidence floor | `PUT /v1/control/confidence_floor {value, scope}` | Raises escalation rate; standard setting 0.80 in Phase 2 and early Phase 3 | Immediate |
| Resume | `POST /v1/control/resume` (requires approver + reason) | Clears kill/pause for scope | Immediate |
Authorisation: kill and pause available to on-call engineers, incident managers and platform operators; resume requires approver role. All control actions audited.
# 9. Prompt-Injection and Input Safety
| Control | Detail |
|---|---|
| Untrusted-data tagging | Ticket text, analyst notes, log extracts, retrieved documents wrapped as data; system prompts instruct to ignore instructions within data |
| Sanitisation | Strip control characters, zero-width characters, hidden markup; truncate per-field |
| Injection scanner | Pattern and classifier scan for instruction-like content ("ignore previous", tool names, credentials requests); hits flagged and removed, event audited |
| Action provenance | TEL rejects any tool call whose parameters contain values originating only from untrusted text and not present in structured payload (e.g. a hostname appearing only in a ticket comment) for Tier ≥ 2 |
| Output handling | LLM outputs never executed as code or shell; tool params must pass schema and bounds |
