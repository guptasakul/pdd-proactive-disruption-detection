# PART A — DESIGN-LEVEL SPECIFICATION
# 1. Purpose and Scope
This component executes the automated incident lifecycle against the organisation's existing ITSM and paging tools without changing their processes: create incident ≤ 60 s, notify on-call, attach diagnostics, link runbook, track SLA, and return analyst feedback to the solution. Agents (TS-15) use the same adapters through the tool execution layer (TS-14) rather than calling ITSM APIs directly.
# 2. Component Decomposition
| Sub-component | Responsibility |
|---|---|
| Integration router | Consumes `decision.incidents`; selects target platforms per routing policy; enforces idempotency |
| Platform adapters | One per platform; maps canonical incident to platform API; handles auth, rate limits, retries |
| Outbox and replay store | Durable queue (PostgreSQL) of pending/failed operations; replays after outage |
| SLA tracker | Timers for acknowledge and resolve SLAs; triggers escalations |
| Feedback collector | Webhooks + polling from ITSM; normalises analyst actions into `feedback.labels` |
| Correlation map | Mapping `incident_id` ↔ external ids (sys_id/number, PD incident id, JSM key, Slack thread ts) |
# 3. Key Design Decisions
| Decision | Rationale |
|---|---|
| Canonical incident model with per-platform adapters | Add or replace ITSM tools without touching the Decision Engine |
| Transactional outbox | Exactly-once effect on external systems despite retries and restarts |
| ITSM remains system of record for incident status | Solution never overrides human-set state; it proposes |
| Webhook-first feedback with reconciliation polling | Timely labels; polling covers missed webhooks |
# 4. Non-Functional Requirements
| ID | Requirement |
|---|---|
| TS08-NFR-001 | `create` event to ITSM incident created ≤ 60 s P99 |
| TS08-NFR-002 | P1 page dispatched ≤ 30 s after ITSM creation (or in parallel if ITSM slow) |
| TS08-NFR-003 | Zero duplicate incidents per `incident_id` across retries/restarts |
| TS08-NFR-004 | Feedback events available on `feedback.labels` ≤ 2 min after analyst action |
# PART B — LOW-LEVEL SPECIFICATION
# 5. Lifecycle Sequence (P1/P2)
```
Decision Engine --decision.incidents(create)--> Router
Router: outbox.insert(op=create, key=incident_id) ; commit
Adapter(ServiceNow): GET incident?correlation_id=<incident_id>  -> none
                     POST /api/now/table/incident {...}           -> sys_id, number
Router: correlation_map.save ; publish ack to Orchestrator (TS-14)
Adapter(PagerDuty): POST /v2/enqueue {routing_key, dedup_key=incident_id, severity, links...}
Adapter(Slack): chat.postMessage(channel=#inc-<service>, blocks=card) -> thread_ts
Router: PATCH incident work_notes += diagnostics, runbook links
SLA tracker: start ack timer (P1 5 min, P2 15 min)
on ack timer expiry -> PagerDuty escalate to next level ; ITSM work note ; Orchestrator notified
```
# 6. Canonical-to-Platform Field Mapping

| Canonical | ServiceNow field | Notes |
|---|---|---|

| `title` | `short_description` | ≤ 160 chars |
| `summary_structured` (+ narrative later) | `description` | |
| severity P1–P4 | `impact`, `urgency` → `priority` | P1: 1/1, P2: 1/2 or 2/1, P3: 2/2, P4: 3/3 (configurable matrix) |
| top affected service | `business_service` | CMDB sys_id |
| affected entities | `cmdb_ci` + Affected CIs related list (`task_ci`) | |
| routing.assignment_group | `assignment_group` | From CMDB service ownership |

| `context.change_ids` | `caused_by` / related change records | Change Management integration |

## 6.2 PagerDuty (Events API v2)

|---|---|

## 6.4 OpsGenie (Alert API)
| Canonical | OpsGenie field |
|---|---|
| `incident_id` | `alias` |
| severity | `priority` P1–P5 (P4 → P4; P5 unused) |
| owner team | `responders[{type: team, name}]` from CMDB |
| details | `details` map, `tags` (layers, mode) |
## 6.5 Slack / Microsoft Teams card
| Element | Content |
|---|---|
| Header | Severity badge, title, ITSM number link |
| Body | Affected services, top root-cause candidate, layers, first detected, blast radius count |
| Actions | Acknowledge · Escalate · Mark false positive · Open runbook · (Tier 3) Approve / Reject action |
| Thread | Progressive updates from Comms agent (TS-15) |
Interactive actions are received on a signed callback endpoint (Slack signing secret / Teams JWT), mapped to the user's corporate identity and authorised against RBAC before any effect.
# 7. Routing Policy
```
routing:
  default: { itsm: servicenow, paging: pagerduty, chat: slack }
  by_org_unit:
    retail-digital: { itsm: jsm, paging: opsgenie, chat: teams }
  by_severity:
    P1: { page: true,  chat_channel: "#major-incidents", exec_summary: true }
    P2: { page: true,  chat_channel: "#inc-{service}" }
    P3: { page: false, chat_channel: "#ops-{team}" }
    P4: { page: false, ticket_queue: "next-business-day" }
  sla:
    ack:     { P1: PT5M,  P2: PT15M, P3: PT30M, P4: P1D }
    resolve: { P1: PT4H,  P2: PT8H,  P3: P3D,   P4: P10D }
```
# 8. Outbox and Idempotency
| Column | Type | Description |
|---|---|---|
| `op_id` | uuid | PK |
| `incident_id` | uuid | Idempotency scope |
| `platform` | text | servicenow · pagerduty · jsm · opsgenie · slack · teams |
| `operation` | text | create · update · comment · resolve · page · escalate |
| `payload` | jsonb | Platform-specific request |
| `status` | text | pending · in_flight · done · failed · dead |
| `attempts`, `next_attempt_at` | int, timestamptz | Exponential backoff 1 s → 5 min, jitter ±20% |
| `external_ref` | text | Returned id |
Rules: a `create` is preceded by a look-up on the platform idempotency key; `update` operations for the same incident and platform are applied in order (per-incident sequence number); after 10 failed attempts an operation becomes `dead` and raises a P2 platform incident.
# 9. Circuit Breaker and Fallback
| Condition | Behaviour |
|---|---|
| 3 consecutive failures to a platform (KRI) | Breaker opens 60 s; half-open probe; operations queue in outbox |
| ITSM breaker open and new P1/P2 | Page via paging platform directly with full payload; post to chat; ITSM record created on recovery and linked |
| Paging platform breaker open | Fallback paging channel (secondary provider, SMS gateway or voice bridge) configured per org unit |
| All channels down | Out-of-band alert to platform on-call via independent dead-man's-switch (TS-11) |
# 10. Bidirectional Feedback
## 10.1 Captured analyst actions
| ITSM action | Detection method | Label emitted |
|---|---|---|
| Resolution code = "False positive" / button "Mark false positive" | Webhook (business rule / automation) | `label=false_positive`, all detection_ids |
| Priority changed | Field-change webhook | `severity_adjustment {from, to, by}` |
| Root cause field / "confirm" on candidate | Field change / card action | `root_cause_confirmed {entity, category}` or `root_cause_corrected {from, to}` |
| Resolution notes | Field on resolve | `resolution_notes {text}` → NLP in TS-13/TS-15 |
| Incident resolved | State change | `resolved {ts, duration, resolution_code}` |
## 10.2 `feedback.labels` schema
```
record FeedbackLabel {
  string label_id; string incident_id; array<string> detection_ids;
  string label_type;   // false_positive | true_positive | severity_adjustment | root_cause_confirmed | root_cause_corrected | resolution_notes | resolved
  map<string> attributes;
  string actor;        // pseudonymised analyst id + role
  long   ts_ms;
  string source_platform;
}
```
Reconciliation: hourly poll of incidents modified in the last 2 h; labels deduplicated by (`incident_id`, `label_type`, external audit id).
# 11. Configuration and Credentials
| Item | Specification |
|---|---|
| ServiceNow | OAuth 2.0 client credentials; integration user with roles `itil` + custom write on `u_detection_source`; rate limit respected via `X-RateLimit` headers |
| PagerDuty | Integration key per service (routing key); REST API key (read) for reconciliation |
| JSM / OpsGenie | API tokens scoped to project/team |
| Slack / Teams | Bot token with `chat:write`, `channels:read`; signing secret for callbacks |
| Storage | All secrets in secrets manager; rotated ≤ 90 days |

# 13. Acceptance Criteria
| ID | Criterion |
|---|---|
| TS08-AC-001 | 1,000 replayed `create` events with forced adapter restarts produce exactly 1,000 ITSM incidents |
| TS08-AC-002 | P99 create latency ≤ 60 s at 50 incidents/min |
| TS08-AC-003 | ITSM outage simulation: P1 still paged via PagerDuty ≤ 60 s; ITSM record backfilled and linked on recovery |
| TS08-AC-004 | Each analyst action in §10.1 produces the correct label within 2 min |
| TS08-AC-005 | Slack/Teams callbacks without valid signature or from unauthorised users are rejected and audited |
