# PART A — DESIGN-LEVEL SPECIFICATION
# 1. Purpose and Scope
Every layer scales independently on observable metrics, within policy bounds, without architectural change or interruption. This specification gives the capacity model, scaling triggers and limits, storage lifecycle policies, and the predictive scaler. Placement and HA are in TS-09.
# 2. Capacity Model
| Dimension | Baseline | Burst | Month-12 planning | Design ceiling without re-architecture |
|---|---|---|---|---|
| Raw ingest | 500k eps | 2M eps (15 min+) | 750k eps | 2M eps sustained |
| Average raw event size (compressed) | 350 B | — | — | — |
| Raw ingest bandwidth | ≈ 175 MB/s | ≈ 700 MB/s | — | — |
| Monitored entities | 120k | — | 200k | 500k |
| Feature vectors/s (all windows) | ≈ 9k | ≈ 20k | 15k | 50k |
| Detections/s | ≈ 300 | ≈ 3k | — | — |
| Incidents/hour | ≈ 20 | ≈ 300 (storm) | — | — |
| Kafka local storage (12 h local of 72 h, RF 3) | ≈ 21 TiB local; remainder tiered to object storage | — | — | — |
Sizing rule of thumb: each Flink TaskManager slot (2 per TM) handles ≈ 12–15k eps for stages 1–2; each inference replica handles ≈ 2k vectors/s at P99 ≤ 50 ms on CPU.
# 3. Key Design Decisions
| Decision | Rationale |
|---|---|
| Scale on work-queue metrics (lag, queue depth) rather than CPU alone | Lag reflects user-visible delay; CPU lags behind bursts |
| KEDA for event-driven scalers; HPA v2 for resource metrics | Native Kafka/Prometheus triggers |
| Flink reactive mode | Parallelism follows TaskManager count without job redeploy |
| Over-partition Kafka 2× from day one | Avoid partition reassignment under load |
| Predictive pre-scaling 10 min ahead | Absorb predictable peaks (business hours, batch windows) without lag |
# 4. Non-Functional Requirements
| ID | Requirement |
|---|---|
| TS12-NFR-001 | Scale-out reaction ≤ 2 min from trigger to new capacity serving (stateless), ≤ 5 min (Flink) |
| TS12-NFR-002 | No data loss or duplicate side-effects during any scale event |
| TS12-NFR-003 | Scale-in protected by stabilisation windows to avoid flapping |
# PART B — LOW-LEVEL SPECIFICATION
# 5. Per-Component Scaling Policies
| Component | Mechanism | Metric | Scale-out trigger | Min / Max | Scale-in |
|---|---|---|---|---|---|
| Flink TaskManagers | KEDA (Kafka scaler) + reactive mode | Consumer lag per partition | Lag > 50,000 | 4 / 32 | Lag < 5,000 for 15 min; −1 TM per 5 min |
| ML Inference | KEDA (Prometheus) | `inference_queue_depth` | > 500 pending | 3 / 20 | < 100 for 10 min |
| Decision Engine | HPA (custom metric) | Processing rate / capacity | > 80% | 3 / 12 | < 40% for 10 min |
| Feature Store (Redis) | Operator + custom controller | Memory %, ops/s per node | Memory > 75% OR ops > 200k/node | 6 / 18 primaries | Manual approval only (slot migration cost) |
| Feature Service | HPA | CPU + RPS | CPU > 60% | 3 / 12 | CPU < 30% 10 min |
| API Gateway | HPA | CPU, active connections | CPU > 60% for 2 min | 2 / 8 | CPU < 30% 10 min |
| ITSM integration workers | KEDA (PostgreSQL scaler) | Outbox pending | > 200 pending | 2 / 10 | < 20 for 10 min |
| OTel gateways | HPA | CPU, exporter queue % | CPU > 70% or queue > 50% | 6 / 24 | 15 min stable |
| LLM gateway / RAG | KEDA | Pending enrichment requests | > 50 | 2 / 12 | See TS-13 |
| Agents | KEDA | Open tasks per agent type | > 20 per replica | 2 / 10 per agent type | See TS-14 |
## 5.1 Example KEDA ScaledObject (Flink TaskManagers)
```
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata: { name: flink-ingest-tm, namespace: streaming }
spec:
  scaleTargetRef: { name: flink-ingest-taskmanager }
  minReplicaCount: 4
  maxReplicaCount: 32
  cooldownPeriod: 900
  advanced:
    horizontalPodAutoscalerConfig:
      behavior:
        scaleUp:   { stabilizationWindowSeconds: 0,   policies: [ { type: Pods, value: 4, periodSeconds: 60 } ] }
        scaleDown: { stabilizationWindowSeconds: 900, policies: [ { type: Pods, value: 1, periodSeconds: 300 } ] }
  triggers:
    - type: kafka
      metadata:
        bootstrapServers: kafka-bootstrap.streaming:9093
        consumerGroup: cg-ingest-aggregate
        topic: raw.application
        lagThreshold: "50000"
        allowIdleConsumers: "false"
      authenticationRef: { name: kafka-mtls }
```
# 6. Kafka Elasticity
| Mechanism | Specification |
|---|---|
| Partitioning | Topics created at 2× required partitions (e.g. `norm.events` 192 for 96 needed); partition count ≥ max consumer parallelism |
| Broker addition | Strimzi scale-up; Cruise Control `add_broker` rebalance with replication throttle 100 MB/s |
| Continuous balancing | Cruise Control goals: RackAware, ReplicaCapacity, DiskCapacity, NetworkIn/OutCapacity, CpuCapacity, LeaderReplicaDistribution; self-healing on broker failure enabled |
| Tiered storage | Segments older than 12 h offloaded; local disk utilisation kept < 70% |
| Quotas | Producer byte-rate quotas per gateway principal to protect cluster from runaway sources |
# 7. Flink Scaling
- Reactive mode: job parallelism = available slots; rescale triggers restart from latest checkpoint (≤ 60 s state at baseline; unaligned checkpoints under backpressure).
- Max parallelism (key groups) set to 4,096 at job creation — immutable — to permit scaling to 32 TMs × 2 slots with even distribution.
- RocksDB state on local SSD; incremental checkpoints to object storage.
# 8. Redis Feature Store Scaling
```
controller loop (every 1 min):
    if any primary memory > 75% or ops/s > 200k for 5 min:
        if primaries < 18: add 1 primary + 1 replica (different AZs)
            migrate slots from hottest primaries (by memory) using CLUSTER SETSLOT / MIGRATE, 500 keys/batch, throttled
            readiness of Feature Service unaffected (clients follow MOVED/ASK redirects)
        else: alert capacity ceiling (P2 platform)
```
Scale-in is a manual, approved change (reverse migration) to avoid repeated slot churn.
# 9. Inference Scaling
- Stateless; any request served by any replica; no session affinity.
- All five models evaluated concurrently per micro-batch → latency ≈ slowest model (~50 ms) not the sum.
- GPU node pool optional: when queue depth > 500 persists 10 min at max CPU replicas, a GPU-backed replica set (2–4) is enabled if the pool exists.
# 10. Predictive Pre-Scaling
| Item | Specification |
|---|---|
| Forecast target | Raw eps per domain and inference queue arrival rate |
| Model | Prophet or seasonal-naive + gradient boosting residual, hourly retrain on 28 days of 1-min data; holiday/business calendar regressors |
| Horizon / lead | 30-min forecast; act 10 min before predicted peak |
| Action | Raise `minReplicaCount` of KEDA objects to `ceil(forecast_p90 / per_replica_capacity × 1.2)`; reset after peak + 30 min |
| Safety | Pre-scaled minimum never exceeds max bounds; forecast error tracked (MAPE target < 15%); disabled automatically if MAPE > 30% for 24 h |
# 11. Storage Tier Lifecycle
| Store | Mechanism | Lifecycle (default) |
|---|---|---|
| Redis | TTLs per key type | 1h-window features expire after 2 h; 1-day histories after 30 d |
| OpenSearch | ILM: rollover daily or 50 GiB/shard | Hot 7 d (SSD) → warm 30 d (HDD) → cold 90 d (object storage snapshots, searchable) → delete 12 months |
| VictoriaMetrics | Independent scaling of vminsert/vmselect/vmstorage; add vmstorage without resharding | 13 months infra; 6 months high-cardinality app metrics; downsampling 5m after 30 d, 1h after 90 d |
| Object storage | Lifecycle rules by prefix | Training data 24 months; model artefacts indefinite; audit 5 years (object lock) |
| Kafka | Tiered storage | 12 h local, 72 h total for raw |
# 12. Cluster Autoscaling
| Node pool | Autoscaler | Min / Max nodes per AZ | Notes |
|---|---|---|---|
| `stream` | Cluster Autoscaler / Karpenter | 2 / 12 | On-demand only |
| `data` | Manual (stateful) | Fixed per sizing | Changes via change request |
| `ml` | Autoscaler | 1 / 8 | GPU sub-pool 0 / 2 |
| `batch` | Autoscaler, spot allowed | 0 / 10 | Training jobs tolerate pre-emption (checkpointing every epoch) |
| `apps` | Autoscaler | 2 / 10 | |
Overprovisioning: a low-priority "balloon" deployment reserves ≈ 10% headroom in `stream` and `ml` pools so that scale-outs do not wait for node provisioning.
# 13. Failure Modes
| Failure | Handling |
|---|---|
| Max replicas reached and lag still rising | Per-source rate limits engage; lowest-priority sources (P4 domains) throttled first; P2 platform incident |
| Scale flapping | Stabilisation windows; flap detector (> 4 direction changes/h) doubles cooldown and alerts |
| Node provisioning delay | Balloon headroom; pre-emption of `pidd-batch` workloads |
| Rebalance overload | Cruise Control throttle; rebalance paused if produce latency P99 > 200 ms |
# 14. Acceptance Criteria
| ID | Criterion |
|---|---|
| TS12-AC-001 | Ramp 500k → 2M eps in 2 min: lag peaks then returns < 50k/partition within 10 min; P99 score latency recovers ≤ 30 s |
| TS12-AC-002 | Scale events during load test produce zero duplicates (exactly-once audit reconciliation) |
| TS12-AC-003 | Redis scale-out from 6 to 9 primaries under load: read P99 stays ≤ 10 ms |
| TS12-AC-004 | Predictive scaler pre-scales before a replayed business-hour peak (capacity in place ≥ 5 min before peak) |
| TS12-AC-005 | 24-h soak at 750k eps without manual intervention |
