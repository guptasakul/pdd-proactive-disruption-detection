# PART A — DESIGN-LEVEL SPECIFICATION
# 1. Purpose and Scope
Defines the five specialist agents that the Orchestrator (TS-14 §9) dispatches. Each agent has one responsibility, a fixed capability profile, an autonomous action set and explicit escalation conditions. All run on the common runtime and tool execution layer (TS-14) under the safety model of TS-16.
# 2. Agent Summary
| Agent | Objective | Trigger | Autonomy ceiling | Primary outputs |
|---|---|---|---|---|
| 01 Triage | Validate, enrich, deduplicate and confirm severity | Every P1–P4 `create`, ≤ 5 s | Tier 1 | Enriched ticket, narrative, entity-service map, severity confidence, duplicate result |
| 02 Diagnostic | Gather evidence and rank root causes; size blast radius | After Triage (parallel with Comms for P1/P2) | Tier 1 (read-only) | Hypotheses, artefact bundle, similar incidents, blast radius, evidence confidence |
| 03 Communications | Notify and keep stakeholders informed | Parallel with Diagnostic for P1/P2; after for P3/P4 | Tier 1 | Pages, bridge updates, status page drafts/posts, exec summaries, ack tracking |
| 04 Remediation | Restore service safely | After Diagnostic with remediation available ≥ confidence threshold | Tier 2 autonomous; Tier 3 with approval | Action log, approval requests, recovery confirmation, rollback record |
| 05 Learning | Turn outcomes into improvement | Resolution; feedback events | Tier 1 (internal writes) | Training labels, RAG updates, PIR, runbook proposals, weekly digest |

# PART B — LOW-LEVEL SPECIFICATION
# 4. Agent 01 — Triage (First Responder)
## 4.1 Behaviour
| Step | Action | Rule |
|---|---|---|
| 1 | Validate payload completeness | Required: entities, severity, timeline ≥ 1 event, routing. Missing → request re-score from Decision Engine (once); still missing → proceed with flag `payload_incomplete` |
| 2 | CMDB enrichment | Resolve entities → business services, tiers, owners; fill `routing` gaps |
| 3 | Duplicate check | Search open incidents (last 6 h) on same entities/services; similarity = 0.5·Jaccard(entities) + 0.3·mode match + 0.2·time overlap; > 0.85 → merge (link child to parent, close child as duplicate); 0.6–0.85 → link as related |
| 4 | Narrative | Invoke F1; on failure use templated summary |
| 5 | Severity confidence | conf = 0.4·S + 0.3·(1 − baseline immaturity) + 0.2·entity resolution ratio + 0.1·cmdb completeness; < 0.70 → escalate for human severity confirmation (incident still proceeds) |
| 6 | Publish | Update ITSM (narrative, enrichment); write `triage` section; signal Orchestrator |
## 4.2 Limits and escalation
Max steps 8; deadline 60 s. Escalate on: severity confidence < 0.70; duplicate merge would close a P1/P2; CMDB owner missing for top service.
# 5. Agent 02 — Diagnostic (Evidence Gatherer)
## 5.1 Behaviour
| Step | Action | Rule |
|---|---|---|
| 1 | Evidence queries | Logs, metrics, traces for affected entities, lookback 2 h (P4: 30 min); result size cap 5,000 lines/query, summarised before LLM |
| 2 | Diagnostic playbook | Execute read-only query set mapped to predicted failure mode (e.g. pool exhaustion → pool metrics, slow queries, lock waits, upstream RPS) |
| 3 | Change correlation | Changes on entities and 1-hop dependencies in last 4 h |
| 4 | Similar incidents | RAG top 5 with confirmed root causes |
| 5 | Hypotheses | Invoke F2 with evidence bundle; merge with Decision Engine ranking: final = 0.5·LLM rank score + 0.5·engine rc score |
| 6 | Blast radius | Dependency traversal depth 3 with live call volumes (refresh of TS-07 §8.2) |
| 7 | Artefact bundle | Query links, chart URLs, trace ids, hypothesis narrative → ISO + ITSM work note |
| 8 | Evidence confidence | Share of top hypothesis evidence items that are direct observations (not inferred) × hypothesis margin |
## 5.2 Diagnostic playbook definition
```
playbook: connection_pool_exhaustion
applies_to_modes: [db_pool_exhaustion, app_thread_starvation]
queries:
  - { tool: metrics.query, q: 'max_over_time(db_pool_active{service="$svc"}[2h])' }
  - { tool: metrics.query, q: 'rate(db_pool_timeouts_total{service="$svc"}[5m])' }
  - { tool: logs.query, q: 'service.name:"$svc" AND error.type:(*Timeout* OR *Pool*)', range: 2h, limit: 500 }
  - { tool: logs.query, q: 'entity.id:"$db" AND event.dataset:db.slowq', range: 2h, limit: 200 }
  - { tool: traces.search, q: 'service=$svc status=error', range: 1h, limit: 50 }
expected_signals: [ pool_active≈max, timeouts↑, slow queries↑ or upstream RPS↑ ]
```
## 5.3 Limits and escalation
Max steps 15; deadline 5 min (P1 target 3 min). Escalate on: no hypothesis with confidence ≥ medium; conflicting top-2 hypotheses with margin < 0.1 on a P1; evidence queries failing.
# 6. Agent 03 — Communications (Stakeholder Coordinator)
## 6.1 Message matrix
| Message | P1 | P2 | P3 | P4 | Generated by | Approval |
|---|---|---|---|---|---|---|
| On-call page | Immediate | Immediate | — (chat notify) | — | Template | None |
| Technical bridge update | Initial + every 15 min | Initial + every 30 min | Initial | — | F3 | None |
| Executive summary | Initial + on major change | On request | — | — | F3 | None (internal) |
| Status page update | If customer-impacting | If customer-impacting | — | — | F3 | Human approval (default) |
| Resolution notice | Yes | Yes | Yes | Ticket note | F3 / template | None |
## 6.2 Behaviour
1. Determine audiences from routing and severity matrix.
2. Invoke F3 for drafts; apply banned-content checks (internal hostnames/IPs on external outputs, speculative cause statements on status page).
3. Send via channel tools; record message ids in ISO.
4. Track acknowledgement: if not acknowledged within SLA (P1 5 min, P2 15 min) → escalate to secondary on-call via paging tool; notify Orchestrator.
5. Periodic updates: diff ISO since last update; skip update if no material change and post "no change, next update at T" line instead.
6. On closure: send resolution notifications to every party notified.
## 6.3 Escalation
Draft rejected by approver twice; status page approval not received in 15 min for P1 (escalate to incident manager); channel failures.
# 7. Agent 04 — Remediation (Autonomous Responder)
## 7.1 Behaviour
| Step | Action | Rule |
|---|---|---|
| 1 | Obtain plan | Matched runbook (TS-07) if fresh; else F4 dynamic runbook (marked generated) |
| 2 | Classify steps | Each step mapped to a registered tool; tier = max(tool tier, runbook suggested tier). Unmapped step → human-only |
| 3 | Precondition | Diagnostic evidence confidence ≥ `remediation.min_evidence` (0.7); top hypothesis consistent with runbook failure mode |
| 4 | Acquire lock | Service lock (TS-14 §7.3) |
| 5 | Execute Tier 1–2 | Allowed set: stateless pod restart, cache flush, connection-pool reset, scale within pre-set bounds, feature-flag toggle declared reversible for this service |
| 6 | Tier 3 request | Approval card: proposed action, expected outcome, risk, blast radius, rollback plan; 10-min timeout → escalate |
| 7 | Verify | Health watch for 5 min: target metrics return within baseline band (|z| < 2) and error rate < pre-incident P95 |
| 8 | Auto-rollback | If measurable degradation within 5 min (error rate +20% relative or latency P95 +30%), execute rollback_ref |
| 9 | Iterate / escalate | Max 5 actions per incident; after 2 failed remediations → escalate with revised hypothesis and full history |
## 7.2 Tier 1–2 action catalogue (initial)
| Tool | Tier | Preconditions | Rollback |
|---|---|---|---|
| `k8s.restart_deployment` | 2 | Stateless; replicas ≥ 2; no rollout in progress | `k8s.rollout_undo` (n/a for restart → health watch) |
| `k8s.scale_deployment` (within HPA bounds) | 2 | Target ≤ max bound | Scale back to previous |
| `cache.flush_keys(pattern)` | 2 | Pattern within service namespace | Warm-up job |
| `db.pool_reset(service)` | 2 | App supports runtime reset endpoint | n/a — health watch |
| `flags.toggle(flag)` | 2 if flag marked `ops_reversible` | Flag owned by affected service | Toggle back |
| `queue.pause_consumer(group)` | 3 | — | Resume |
| `deploy.rollback(release)` | 3 | Deployment correlated (TS-07 F2) | Redeploy |
| `scale.beyond_bounds` | 3 | Capacity available | Scale back |
## 7.3 Escalation
Precondition not met; lock unavailable > 2 min; any guardrail block; verification fails; Tier 4 step encountered (handoff with prepared action and guidance).
# 8. Agent 05 — Learning (Continuous Improver)
## 8.1 Behaviour
| Step | Action | Output |
|---|---|---|
| 1 | Parse notes | F6 on resolution notes and analyst comments | Root-cause class, resolution method, contributing factors |
| 2 | Detection quality | Proactive? (first detection before first user report/external alert); severity correct? (final vs. initial); hypothesis hit? (confirmed ∈ top 3) | Quality record per incident |
| 3 | Labels | TP/FP and severity labels to `feedback.labels` (deduplicated with TS-08 labels) | Training labels |
| 4 | Knowledge base | Index incident (summary, root cause, resolution) into RAG | Updated semantic memory |
| 5 | PIR | F5 for P1/P2 (and on request); submit to knowledge management for review | PIR document |
| 6 | Runbook gaps | If remediation used a generated runbook or human-only steps → draft runbook proposal for service owner review | Runbook PR |
| 7 | Pattern analysis (weekly) | 30-day rolling: recurring failure modes, systematic FP sources, suppression candidates, agent escalation reasons | Weekly digest to platform team |
## 8.2 Escalation
PIR grounding failure; contradictory labels (analyst FP vs. confirmed root cause) → queue for human adjudication.
