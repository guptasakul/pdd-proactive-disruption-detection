# PART A — DESIGN-LEVEL SPECIFICATION
# 1. Purpose and Scope
Defines how "normal" is learned and kept current. Covers population, individual, contextual and peer-group baselines; the bootstrap period for new entities; and the end-to-end model lifecycle: data extraction, training, evaluation, registration, shadow deployment, promotion, monitoring, drift-triggered retraining and rollback. Governance policy (approval authority, documentation, audit) is in TS-10.
# 2. Component Decomposition
| Sub-component | Technology | Responsibility |
|---|---|---|
| Baseline jobs | Spark/Flink batch on Iceberg (TS-04 offline store) | Compute four baseline layers; publish to `ref.baselines` |
| Peer clustering job | Spark ML (k-means), monthly | Assign peer groups |
| Training pipeline | Kubeflow Pipelines / Argo Workflows as Kubernetes Jobs | Extract, train, tune, evaluate, register |
| Hyperparameter search | Optuna (TPE), bounded trials | Tuning on retrain or F1 shortfall |
| Model Registry | MLflow Model Registry (or equivalent) | Versions, lineage, metrics, stage, approvals |
| Evaluation service | Batch job + shadow comparator | Offline metrics, shadow precision/recall, promotion decision |
| Drift monitor | Daily job + streaming PSI estimator | KS and PSI on features and scores |
# 3. Key Design Decisions
| Decision | Rationale |
|---|---|
| Baselines computed offline and broadcast, not learned inside streaming jobs | Reproducible, auditable, cheap to recompute after CMDB-driven invalidation |
| Exponential decay with 4× recency weight for last 7 days | Tracks legitimate evolution without forgetting weekly seasonality |
| Contextual baselines by hour-of-day and day-of-week rather than a single seasonal model | Interpretable for analysts, robust with 28 days of data |
| Daily retraining with automatic promotion only via shadow comparison | Freshness without unreviewed regressions |
| Auto-rollback on FP surge | Bounded blast radius of a bad promotion |

# PART B — LOW-LEVEL SPECIFICATION
# 5. Baseline Layers
| Layer | Key | Window | Statistics stored | Refresh | Use |
|---|---|---|---|---|---|
| L1 Population | (entity_class, feature, window) | 28 d | mean, std, p01/p05/p50/p95/p99, t-digest | Daily | New entities; normalisation in M1 |
| L2 Individual | (entity_id, feature, window) | 28 d, exp. decay, last 7 d weighted 4× | weighted mean, weighted std, p95, n_eff | Daily + on invalidation | `beh.z_individual` |
| L3 Contextual | (entity_id, feature, context) where context ∈ {hour 0–23} × {weekday/weekend} and day-of-week 0–6 | 28 d | mean, std | Daily | SPC limits, contextual z |
| L3 Post-deploy | (entity_id, feature) | Derived | widened limits (×1.33 σ) for 30 min | Event-driven | Deployment guard |
| L3 Maintenance | (entity_id) | Event-driven | suppressed | Event-driven | No scoring for in-scope entities |
| L4 Peer group | (peer_group_id, feature, window) | 30 d | mean, std, p95 | Monthly clustering; daily stats | `beh.z_peer` |
## 5.1 Individual baseline weighting
```
for observation at age a days (0 ≤ a < 28):
    w(a) = exp(-λ a) * (4 if a < 7 else 1)        # λ = ln(2)/14 (14-day half-life)
μ = Σ w x / Σ w
σ² = Σ w (x − μ)² / (Σ w − Σ w² / Σ w)            # reliability-weighted unbiased variance
n_eff = (Σ w)² / Σ w²
publish only if n_eff ≥ n_min (default 288 five-minute points ≈ 1 day)
```
## 5.2 Contextual baselines
Hour-of-day baselines require ≥ 3 observations per hour bucket; buckets below this borrow from the adjacent ±1 hour buckets (weighted 0.5) and then from L2. Day-of-week baselines require ≥ 2 observations per day.
## 5.3 Peer groups
```
input: for each entity of class c, 30-day profile vector = [p50, p95, std] of 12 curated features, log-scaled, z-normalised per class
for k in 2..min(20, n_entities/10):
    fit KMeans(k, n_init=10, seed fixed)
    score silhouette(k)
k* = argmax silhouette; require silhouette ≥ 0.25 else peer layer disabled for class c
assign peer_group_id = <class>:<k*>:<cluster>; persist with assignment history
```
Entities move between groups only at monthly recomputation; moves are logged.
## 5.4 Baseline invalidation
A CMDB change of type {hardware replacement, major version upgrade, re-platform, capacity change > 50%} on an entity invalidates its L2 and L3 baselines: the entity drops to Bootstrap-1 state with population and peer baselines, and history after the change date is used to rebuild.
# 6. Bootstrap State Machine
| State | Entry | Active baselines | Model behaviour | Exit |
|---|---|---|---|---|
| Bootstrap-0 | First seen (day 0) | L1 population | SPC and Isolation Forest on population stats; LSTM inactive | n_eff for 3 days |
| Bootstrap-1 | Day 3 | L1 + L2 (low confidence) | Composite score halved (threshold elevated 2×) | Day 7 |
| Bootstrap-2 | Day 7 | All layers, reduced weight | Composite score ÷ 1.5 (threshold elevated 1.5×); analyst review encouraged | Day 14 and contextual buckets ≥ 80% populated |
| Mature | Day 14+ | All layers | Standard thresholds | Invalidation → Bootstrap-1 |
State is stored per entity in `ref.baselines` as `baseline_maturity` and propagated on every feature vector (TS-04).
# 7. Baseline Publication Format (`ref.baselines`, compacted)
```
record BaselineRecord {
  string key;                 // <layer>|<entity_or_class_or_group>|<feature>|<window>|<context>
  string layer;               // population | individual | contextual | peer
  double mean; double std; double p95; double p99;
  double n_eff;
  long   computed_at_ms;
  string data_snapshot_id;    // Iceberg snapshot
  string maturity;            // for individual entries
}
```
# 8. Model Lifecycle
## 8.1 Stages
```
[Data extraction] -> [Train] -> [Tune (conditional)] -> [Offline evaluation] -> [Register: Candidate]
   -> [Shadow 48 h] -> [Promotion gate] -> [Production] -> [Monitor] -> (drift | regression) -> retrain / rollback
                                     \-> [Rejected] (logged with reason)
```
## 8.2 Training pipeline steps
| Step | Detail |
|---|---|
| 1 Extract | Point-in-time training set from Iceberg: last 90 days of vectors + labels; snapshot id recorded |
| 2 Validate data | Great Expectations suite: null ratios, ranges, label counts per class; abort on failure |
| 3 Train | Per model spec in TS-05; seeds fixed; resources 16 vCPU / 64 GiB per job (GPU for M1/M4 optional) |
| 4 Tune | Run only if previous F1 < target or weekly schedule; Optuna, max 40 trials, 2 h budget |
| 5 Calibrate | Fit normalisation quantiles (q99, q999) on validation scores; refit fusion precisions P_md |
| 6 Evaluate | Held-out last 14 days (time-based split) → precision, recall, weighted F1, PR-AUC, per-class and per-domain metrics, bias slices (tier, region, time-of-day) |
| 7 Register | Artefact (ONNX), metrics, data snapshot, code commit, config, model card; stage = Candidate |
## 8.3 Promotion gate (automatic for minor versions)
| Condition | Rule |
|---|---|
| Offline quality | Candidate F1 ≥ production F1 − 0.005 AND precision ≥ production precision − 0.01 |
| Shadow quality (48 h) | On analyst-labelled shadow detections: precision and recall both ≥ production |
| Volume sanity | Shadow detection volume within [0.7×, 1.3×] of production |
| Bias slices | No slice F1 drops > 0.05 vs. production |
| Approval | Minor version: automated gate + peer review record. Major version (architecture or feature-set change): ML Governance Committee / CAB approval (TS-10) |
## 8.4 Post-promotion monitoring and rollback
- Rolling 6-hour comparison of auto-created-ticket FP rate vs. pre-promotion 7-day baseline.
- If FP rate > 2× baseline within 6 h → automatic rollback to previous Production version (registry stage flip + `control.config` event); incident raised to ML Engineering.
- Rolled-back versions are marked `Rejected-PostPromotion` and cannot be re-promoted without a new version.
## 8.5 Drift detection
| Test | Target | Schedule | Threshold | Action |
|---|---|---|---|---|
| PSI | Top 30 features per class (by SHAP importance) | Daily (10 bins, training distribution as reference) | > 0.2 any feature (KRI) | Immediate retraining signal |
| PSI | Composite and per-model scores | Daily | > 0.2 | Retraining + calibration refresh |
| KS two-sample | Same features | Daily | p < 0.01 and D > 0.1 | Logged; retrain if persists 3 days |
| Performance | Weighted F1 on rolling labelled set | Hourly | < 0.85 | Retrain with tuning |
```
PSI = Σ_i (a_i − e_i) · ln(a_i / e_i)      # a = actual bin share, e = expected bin share, ε = 1e-4 floor
```

# 11. Failure Modes
| Failure | Handling |
|---|---|
| Training job fails | Production model unchanged; retry once; alert ML Engineering; daily-retrain SLO tracked |
| Data validation fails (label flood, nulls) | Abort; investigate source; no promotion that day |
| Baseline job late | Previous baselines retained; `baseline_stale` flag after 36 h; P3 incident |
| Registry unavailable | Inference keeps loaded models; no promotions until restored |
| Drift caused by legitimate business change (e.g. festive peak) | Analyst can declare a "known regime" calendar entry: drift alerts suppressed, contextual baselines tagged |
