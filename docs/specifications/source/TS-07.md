# PART A — DESIGN-LEVEL SPECIFICATION
# 1. Purpose and Scope
The Decision Engine converts a stream of per-entity detections into a small number of well-formed, correctly prioritised incident decisions. It groups related detections across layers, applies suppression, assigns severity with an auditable rationale, and builds the payload consumed by ITSM integration (TS-08) and the agent network (TS-14). It does not call external ITSM APIs and does not invoke LLMs.
# 2. Processing Pipeline
| Step | Function |
|---|---|
| D1 Correlate | Group detections into candidate incidents by topology and time |
| D2 Suppress | Apply five false-positive filters in fixed order |
| D3 Score severity | Compute severity score and map to P1–P4 |
| D4 Root cause & blast radius | Rank root-cause candidates; traverse dependency graph |
| D5 Build payload | Assemble incident payload with diagnostic links and runbook match |
| D6 Emit / update | Publish new incident or update to existing open incident |
# 3. Key Design Decisions
| Decision | Rationale |
|---|---|
| Stateful correlation in Flink keyed by service cluster | Holds open candidate incidents in memory with exactly-once semantics |
| Policy as declarative rules (YAML) evaluated by an embedded engine | Auditable, testable, changeable through GitOps without code release |
| Deterministic severity formula, not ML | Severity must be explainable and stable; ML provides inputs, policy decides |
| Suppression produces a logged decision, never a silent drop | Every suppressed detection remains reviewable and feeds learning |
# 4. Non-Functional Requirements
| ID | Requirement |
|---|---|
| TS07-NFR-001 | Detection to decision emitted ≤ 10 s P99 (excluding minimum-duration hold) |
| TS07-NFR-002 | Throughput ≥ 5,000 detections/s per replica set; 3–12 replicas |
| TS07-NFR-003 | 100% of decisions (emit, suppress, merge) written to audit trail with rule ids |
# PART B — LOW-LEVEL SPECIFICATION
# 5. D1 — Correlation
## 5.1 Grouping rules
```
on detection d:
    cluster_key = service_cluster(d.entity_id)          # connected component of CMDB service graph, max 2 hops
    candidates = open_candidates[cluster_key]
    for c in candidates:
        if overlaps_in_time(c, d, gap ≤ 10 min) and (
             graph_distance(c.entities, d.entity_id) ≤ 2 or
             d.predicted_mode == c.predicted_mode or
             shared_change_id(c, d)):
            merge(d into c); return
    create new candidate c' with d
candidate closes when no new detection for 15 min AND composite score < 0.35 for all members
```
## 5.2 Candidate incident state
| Field | Description |
|---|---|
| `candidate_id` | UUIDv7 |
| `entities` | Set with first-seen and max score per entity |
| `layers` | Set of domains/layers involved (network, security, application, database, platform, business) |
| `max_score`, `score_series` | Highest composite score; time series for timeline |
| `first_detection_ts`, `last_detection_ts` | |
| `business_impact` | True if any `biz.kpi` entity in cluster has detection ≥ 0.6 or SLA-breach signal |
| `status` | holding · suppressed · emitted · closed |
# 6. D2 — False-Positive Suppression Filters
Filters execute in order; the first filter that matches determines the outcome. Each records `suppression.rule_id` and `suppression.outcome`.
| # | Filter | Logic | Outcome |
|---|---|---|---|
| F1 | Maintenance window | All candidate entities inside an active maintenance window scope | `suppressed_maintenance` (logged). If any entity outside scope → filter does not apply to those entities; candidate continues with them only |
| F2 | Recent deployment correlation | Deployment on any candidate entity or direct dependency started ≤ 30 min before first detection | Not suppressed: tagged `deployment_correlated`, routed to deployment owner, severity capped at P3 unless `business_impact` |
| F3 | Known flap | Entity on known-flap register | Require `confirm_rounds` (default 3) consecutive windows above threshold before proceeding |
| F4 | Minimum duration | Candidate age < `min_duration` (default 3 min) and score not above P1 fast-path threshold (0.9 with business impact) | Hold; if resolves before min duration → `suppressed_transient` (logged, no incident) |
| F5 | Analyst feedback rules | Match against active suppression rules derived from confirmed false positives (TS-11) | `suppressed_feedback_rule:<rule_id>` |
## 6.1 Suppression rule format (F5)
```
rule_id: SUP-2026-0142
status: active                     # proposed | active | archived
created_from: [INC0081234, INC0081290, INC0081311]
match:
  entity_class: cmdb_ci_db_instance
  service: reporting-db
  features_all:
    - { name: stat.metric_cpu_mean.5m, op: between, value: [0.85, 0.97] }
  time_window: { cron: "0 1 * * *", duration: PT45M }   # nightly batch
action: suppress
expires_at: 2027-01-14T00:00:00Z
approved_by: user:ops-lead-1
```
# 7. D3 — Severity Scoring
## 7.1 Inputs
| Input | Symbol | Range |
|---|---|---|
| Max composite score in candidate | S | 0–1 |
| Number of distinct layers with detection ≥ 0.6 | L | 1–6 |
| Max entity criticality (CMDB 1–5, 5 = critical) | C | 1–5 |
| Business impact flag | B | 0/1 |
| Predicted time to impact (M4 horizon, min) | H | 15/30/60/none |
| Blast radius (count of tier-1 services at risk) | R | ≥ 0 |
## 7.2 Severity score
```
sev = 0.40*S + 0.15*min(L-1,3)/3 + 0.20*(C-1)/4 + 0.15*B + 0.05*urgency(H) + 0.05*min(R,5)/5
urgency(15)=1.0, urgency(30)=0.6, urgency(60)=0.3, urgency(none)=0
```
## 7.3 Mapping to P1–P4 (with hard rules)
| Severity | Rule (first match) |
|---|---|
| P1 Critical | B = 1 AND C ≥ 4 AND L ≥ 2 AND S ≥ 0.8; OR sev ≥ 0.80 |
| P2 High | L ≥ 2 AND S ≥ 0.7; OR sev ≥ 0.62 |
| P3 Medium | Single layer with S ≥ 0.6 (high-confidence threshold); OR sev ≥ 0.45 |
| P4 Low | Otherwise, if S ≥ 0.35; non-critical systems (C ≤ 2) capped at P3 unless B = 1 |
Caps and floors: `deployment_correlated` caps at P3 unless B = 1; Bootstrap-1/2 entities cap at P2 unless B = 1. The rationale string lists every input value and the matching rule, e.g. `P2: rule L≥2∧S≥0.7 (S=0.78, L=3, C=4, B=0, H=30, R=2, sev=0.66)`.
## 7.4 Response actions by severity
| Severity | Action (executed by TS-08) |
|---|---|
| P1 | Immediate incident; page on-call; invoke major-incident protocol |
| P2 | Incident; notify on-call on primary channel ≤ 5 min |
| P3 | Incident; notify team on secondary channel; response ≤ 30 min |
| P4 | Next-business-day ticket; add to watch list; auto-escalate to P3 if score rises ≥ 0.15 or a second layer joins |
# 8. D4 — Root Cause Candidates and Blast Radius
## 8.1 Root-cause ranking
```
for each entity e in candidate:
    rc(e) = 0.35*earliest_rank(e)          # earlier first detection → higher
          + 0.25*graph_upstreamness(e)     # from GNN propagation path: sources score high
          + 0.20*S_max(e)
          + 0.10*change_proximity(e)       # change on e within 4 h
          + 0.10*mode_match(e)             # M4 failure mode anchored at e
return top 5 by rc with evidence list (signals, timestamps, model contributions)
```
## 8.2 Blast radius
Breadth-first traversal of CMDB dependency graph from top root-cause candidate, downstream (consumers) to depth 3, weighted by observed call volume. Output: list of services with depth, tier, owner and `at_risk_score = edge_weight_product × criticality`.

## 9.1 Diagnostic link construction
Links are generated from templates with entity identifiers and a time range `[first_detection − 30 min, now]`, e.g. OpenSearch Discover query `entity.id:"<id>" AND event.severity>=50`, Grafana dashboard with `var-service=<name>&from=<ts>&to=now`, trace search `service.name=<name> status=error`. Templates live in configuration per tool.
## 9.2 Runbook matching
Score = 0.6 × (failure-mode match) + 0.3 × (service match) + 0.1 × (signal keyword overlap). Runbooks older than 90 days since review are flagged `stale=true` (triggers dynamic runbook generation in TS-13).
# 10. D6 — Update Semantics
| Situation | Event |
|---|---|
| New candidate passes filters | `create` |
| New entities/layers join open incident | `update` (timeline, entities, blast radius) |
| Severity rises by ≥ 1 level | `escalate` |
| Severity falls and stays lower for 15 min | `deescalate` (never below P3 for incidents that were P1) |
| All scores < 0.35 for 30 min | `auto_resolve_candidate` (resolution confirmed by human or agent per TS-15) |

# 12. Failure Modes
| Failure | Handling |
|---|---|
| CMDB graph missing for entity | Correlate by time + predicted mode only; blast radius = "unknown"; severity uses C = 3 default and flags `cmdb_gap` |
| Maintenance calendar stale | F1 disabled (fail open — no suppression) and P3 platform incident raised |
| Detection flood (> 10× normal) | Storm mode: correlation window doubled, P4 emission paused, single "detection storm" P2 platform incident |
| State backend loss | Restore from checkpoint; candidates re-formed from replay of last 30 min of `ml.detections` |
