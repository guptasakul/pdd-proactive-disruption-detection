# PART A — DESIGN-LEVEL SPECIFICATION
# 1. Purpose and Scope
Turns the specifications into a governed delivery programme: what is built in each phase, what must be true to enter and exit each phase, how success is measured, and how the programme is accepted. Core detection (Sections 10–11 of the white paper) and the GenAI/agent rollout (14E) are integrated into one phase plan.
# 2. Integrated Phase Plan
| Phase | Months | Core detection objective | GenAI / agent objective | Automation level |
|---|---|---|---|---|
| 1 Foundation | 1–3 | Pipeline live; top 5 sources; 30-day baseline collection; dashboards | RAG built; narrative and hypotheses drafted in tickets for analyst review | No automated incidents |
| 2 Shadow | 4–6 | Models trained; shadow detection; daily analyst review; tune to < 5% FP; ITSM integration tested | Triage agent on all incidents; Comms agent on P1/P2; humans review all agent actions | Tier 1 agents; incidents still human-raised |

## 5.5 Gate governance
Each gate is reviewed by the programme board with ML Governance Committee representation. Outcomes: Pass, Pass with conditions (actions with dates), or Hold. A phase cap (TS-16 §4.2) cannot be lifted until the gate passes.
# 6. KPI Definitions
## 6.1 Core detection KPIs
| KPI | Formula | Data source | Baseline method | Month-12 target |
|---|---|---|---|---|
| MTTD reduction | 1 − (MTTD_now / MTTD_baseline); MTTD = mean(incident_raised_ts − earliest_precursor_ts) | ITSM + detection audit; earliest precursor determined in post-incident review | 30-day pre-implementation window, same severity mix | ≥ 70% |
| MTTR reduction | 1 − (MTTR_now / MTTR_baseline); MTTR = mean(resolved_ts − raised_ts) | ITSM | 90-day pre-implementation | ≥ 40% |
| False positive rate | FP-labelled auto-created tickets / auto-created tickets (P1–P3), rolling 30 d | `feedback.labels` | — | < 5% |
| Detection coverage (proactive) | Confirmed incidents where solution alerted before user/external report / all confirmed incidents | ITSM + audit | — | > 75% |
| Alert volume reduction | 1 − (alerts reaching humans now / baseline) | Paging + ITSM | 30-day baseline | ≥ 30% |
| P1 incident rate | 1 − (P1 count per month now / baseline monthly average) | ITSM | 6-month baseline | ≥ 25% reduction |
| Analyst feedback rate | P1/P2 auto-incidents labelled within severity SLA / P1/P2 auto-incidents | `feedback.labels` | — | > 80% |
| Model accuracy | Weighted F1 on held-out labelled validation set, monthly | TS-06 evaluation | — | > 0.85 |
## 6.2 GenAI and agent KPIs
| KPI | Formula | Baseline | Month-12 target |
|---|---|---|---|
| Mean time to acknowledge P1 | mean(first human ack − incident created) | 8 min | < 90 s |
| Triage accuracy | Incidents where severity and service routing unchanged by analyst / reviewed incidents | 60% (manual) | ≥ 92% |
| Root-cause top-3 hit rate | Confirmed root cause ∈ agent's top 3 / incidents with confirmed root cause | n/a | ≥ 75% |
| Remediation automation rate | Tier 1–2 actions executed autonomously / applicable Tier 1–2 actions | 0% | ≥ 60% |
| MTTR reduction (agent contribution) | Matched-pair comparison: incidents with vs. without Remediation agent action, same failure mode | Baseline | 40% additional |
| Agent escalation rate | Incidents needing human takeover before resolution / incidents | n/a | < 20% |
| PIR automation | PIRs generated by Learning agent without human drafting / PIRs | 0% | ≥ 90% |
| LLM factual accuracy | Grounded quantitative claims / quantitative claims checked | n/a | ≥ 98% |
| Analyst satisfaction | Quarterly survey mean (1–5) | Baseline survey | ≥ 4.0 |

# 7. KRI Register
| KRI | Threshold | KPIs at risk | Response (spec) |

| Feature Store availability | P99 > 10 ms or < 99.9% | F1, MTTD | Scale (TS-04, TS-12) |

| (Added) Agent escalation rate | > 30% weekly | MTTR, MTTA | Review agent profiles (TS-15) |
| (Added) Label backlog | > 20% of P1/P2 unlabelled after SLA | F1, FP | Analyst capacity review (TS-17) |
# 8. Measurement Rules
- Baselines are frozen at Phase 1 exit and documented with query definitions; changes require programme board approval.
- KPIs computed by version-controlled queries; dashboard shows formula, data freshness and sample size.
- Incidents excluded from KPI denominators: planned changes, test incidents, incidents in sources not yet onboarded (coverage reported separately per onboarded domain).
- Earliest precursor timestamp for MTTD is set during post-incident review (Learning agent proposal, human-confirmed).
- Monthly report to technology leadership; weekly KRI report to platform team (TS-10 §10).
# 9. Risk Register (programme)
| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| CMDB quality below threshold | High | GNN, routing and blast radius degraded | R2 gate; CMDB data-quality KPI; GNN weight cap (TS-05) |
| Insufficient labelled history for Transformer | Medium | Precursor detection weaker | Enable at 12 months corpus; synthetic fault injection labels |
| Analyst labelling fatigue | Medium | Feedback loop starves | Low-effort label buttons; F6 note parsing; label backlog KRI |
| Over-automation incident caused by agent | Low | High | Phase caps, guardrails, kill switch, reversal |
| LLM cost overrun | Medium | Budget | Token budgets and degradation policy (TS-13 §10) |
| Precursor premise weaker in target estate | Medium | MTTD target at risk | Phase 1 back-test; re-baseline targets at Phase 1 gate |
