# PART A — DESIGN-LEVEL SPECIFICATION
# 1. Purpose and Scope
Defines where and how every component runs: cluster layout, resource specifications, placement and anti-affinity, persistent storage, high availability across three availability zones, cross-region disaster recovery, and the platform security baseline. Elastic scaling behaviour is specified in TS-12.
# 2. Deployment Topology
| Element | Specification |
|---|---|
| Kubernetes | CNCF-conformant ≥ 1.29; managed (EKS/AKS/GKE) or on-premises (OpenShift/Rancher/vanilla) |
| Clusters per region | 1 production cluster (3 AZs) + 1 non-production cluster; optional dedicated data cluster for Kafka/OpenSearch when on bare metal |
| Node pools | `system` (control add-ons), `stream` (Flink, Kafka if in-cluster), `data` (Redis, OpenSearch, VictoriaMetrics, PostgreSQL), `ml` (inference; optional GPU), `batch` (training jobs, spot/pre-emptible allowed), `apps` (decision, integration, agents, gateway) |
| Service mesh | Istio or Linkerd, mTLS STRICT |
| GitOps | Argo CD (or Flux) per cluster, app-of-apps per environment |
| Ingress | Internal API gateway (2–8 replicas) for UI, callbacks and agent APIs; no public ingress except signed chat callbacks via WAF |

# 6. Placement and Availability Controls
```
# applied to every stateless Deployment
topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: topology.kubernetes.io/zone
    whenUnsatisfiable: DoNotSchedule
podAntiAffinity: preferredDuringScheduling on kubernetes.io/hostname
PodDisruptionBudget: minAvailable = max(2, ceil(0.66 * replicas))
priorityClassName: pdd-critical | pdd-standard | pdd-batch
```
| Stateful component | Replication | AZ guarantee |
|---|---|---|
| Kafka | RF 3, `min.insync.replicas` 2, rack-aware | One replica per AZ |
| Redis | Replica per primary in different AZ | Cluster survives AZ loss with replica promotion |
| OpenSearch | 1 replica per shard, shard allocation awareness by zone | Forced awareness |
| VictoriaMetrics | `-replicationFactor=2` on vminsert across zones | Yes |
| PostgreSQL | Synchronous replica in second AZ | Yes |
| Flink | Checkpoints in regional object storage; JobManager HA | Restart in surviving AZs |
Priority classes: `pdd-critical` (collectors, Kafka, Flink, inference, decision, integration), `pdd-standard` (GenAI, agents, UI), `pdd-batch` (training; pre-emptible).
# 7. Multi-Region and Disaster Recovery
## 7.1 Modes
| Mode | Description | Use |
|---|---|---|
| Active-active | Each region runs a full independent stack on its own telemetry; global correlator consumes `ml.detections` and `decision.incidents` from all regions | Multi-region estates |
| Warm standby | Secondary region has stack at minimum replicas; Kafka MirrorMaker 2 replicates `raw.*`, `ref.*`, `feedback.labels`; models and baselines synced | Single-primary estates |
## 7.2 Replication matrix
| Data | Mechanism | Lag target |
|---|---|---|
| `raw.*` (for DR replay) | MirrorMaker 2, offset sync enabled | < 5 min (RPO) |
| `ref.*` (CMDB, baselines, TI) | MirrorMaker 2 | < 5 min |
| Model artefacts, registry DB | Object storage cross-region replication; PostgreSQL async replica | < 15 min |
| Outbox / ISO state | PostgreSQL async replica; ISO rebuilt from audit + ITSM on failover | < 5 min |
| OpenSearch logs | Cross-cluster replication for last 7 days (optional) | Best effort |
## 7.3 Failover runbook (warm standby)
| Step | Action | Budget |
|---|---|---|
| 1 | Declare DR (human approval — Tier 4 per TS-16) | — |
| 2 | DNS / global LB failover for UI, callbacks, collectors' gateway endpoints | < 60 s |
| 3 | Scale secondary to production minimums (HPA min override) | ~5 min |
| 4 | Flink jobs start from mirrored offsets; consumer catch-up | < 5 min |
| 5 | Inference ready, models loaded; decision engine rebuilds candidates from last 30 min | < 5 min |
| 6 | Verify synthetic canary incident end-to-end | < 2 min |
| Total | | < 15 min (RTO) |
DR is exercised quarterly; results recorded against TS09-NFR-002.
# 8. Network Segmentation
| Flow | Allowed | Control |
|---|---|---|
| Sources → OTel gateway | Defined ports (4317/4318, 6514 syslog-TLS, 2055/4739 flow) from source VLANs | Firewall + NetworkPolicy |
| Namespace → namespace | Only declared dependencies (e.g. `ml` → `features` gRPC) | Default-deny NetworkPolicy + mesh AuthorizationPolicy |
| Agents → target infrastructure APIs | Only via tool execution layer egress gateway; per-tool destination allow-list | Egress gateway + mesh |
| GenAI → LLM provider | Via LLM gateway egress only; private endpoint / VPC peering | Egress allow-list |
| Chat callbacks inbound | WAF → API gateway → integration namespace | Signature verification |
# 9. Security Controls
| ID | Control |
|---|---|
| TS09-SEC-001 | mTLS between all services via mesh; certificates from cert-manager with internal CA; rotation ≤ 24 h for workload certs |
| TS09-SEC-002 | Encryption at rest AES-256 for all PVs, object storage and backups; keys in KMS/HSM; customer-managed keys where available |
| TS09-SEC-003 | Human access via OIDC/SAML SSO + MFA; Kubernetes RBAC mapped to roles in TS-01 SEC-002; break-glass accounts sealed and audited |
| TS09-SEC-004 | Workload identity (IRSA / Workload Identity / SPIFFE) — no static cloud credentials in pods |
| TS09-SEC-005 | Pod Security Standards `restricted` on all namespaces except documented exceptions (`observability` host agents) |
| TS09-SEC-006 | Admission control: signed images only (cosign), SBOM attached, no `latest` tags, resource limits mandatory |
| TS09-SEC-007 | Container images scanned in CI and nightly; critical CVEs block deployment; high CVEs fixed ≤ 30 days |
| TS09-SEC-008 | Privileged operations (kubectl exec, secret reads, Argo sync overrides) logged to immutable audit trail and SIEM |
| TS09-SEC-009 | Backups: daily snapshots of PostgreSQL, registry, OpenSearch indices (critical), retained 35 days, restore tested monthly |
# 10. Failure Modes
| Failure | Handling |
|---|---|
| Single node loss | Rescheduled; PDBs keep quorum; DaemonSet gap logged |
| AZ loss | Topology spread ensures ≥ 2/3 capacity; HPA scales in surviving AZs; Kafka/Redis/PG failover automatic |
| Region loss | Warm-standby failover per §7.3 or active-active continues in remaining regions |
| Mesh control-plane failure | Data plane continues with cached config/certs (certs valid 24 h) |
| KMS unavailable | Running pods continue with cached data keys; new volume mounts fail → P1 platform incident |
# 11. Acceptance Criteria
| ID | Criterion |
|---|---|
| TS09-AC-001 | AZ-failure game day: zero acknowledged event loss; throughput recovered ≤ 10 min |
| TS09-AC-002 | DR failover exercise meets RPO < 5 min and RTO < 15 min with canary incident passing |
| TS09-AC-003 | Policy audit: 100% of workloads comply with PSS restricted (or approved exception), signed images, limits set |
| TS09-AC-004 | Penetration test of ingress and agent egress paths: no critical/high findings open at go-live |
